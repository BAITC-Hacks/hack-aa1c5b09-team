План работы команды над MVP

Цель: пользователь описывает потребность, уточняет её с помощью ИИ, проверяет и публикует карточку. Другие пользователи предлагают решения, владелец выбирает одно из них.

Распределение соответствует договорённости: один участник делает фронтенд, второй — перенос и расширение основного бэкенда, третий — ИИ-модуль на Java. Имена и календарные сроки пока не заданы; порядок ниже обозначает зависимости, а не длительность работы.

| Участник | Ответственность | Результат |
|---|---|---|
| 1 | Фронтенд | Полный пользовательский путь в браузере |
| 2 | Основной бэкенд | Пользователи, карточки, предложения, права и бизнес-правила |
| 3 | ИИ-модуль | Работающий Java-модуль уточнения с API, сохранением диалогов и обработкой ошибок |

Один репозиторий, одно приложение Spring Boot, PostgreSQL. Фронтенд обращается к REST API. Базовый вариант интерфейса — HTML/CSS/JavaScript со статическими файлами в `src/main/resources/static`; это позволяет отдавать страницы и API с одного адреса. Java-код разделяется на пакеты `identity`, `needs`, `proposals`, `clarification`. У каждого разработчика своя локальная база, схема обновляется миграциями Flyway.

Существующий проект изучен по исходникам [Project_university, коммит a57630e](https://github.com/Anuar366/Project_university/tree/a57630e73e362d709e518a67279de82e55619c4d). Он использует ASP.NET Core MVC, Entity Framework Core, PostgreSQL и Razor. Перенос означает переписывание нужной логики на Java с адаптацией предметной области. Перенос существующих пользовательских данных в этот план не входит: необходимость и способ такого переноса нужно определить отдельно.

**Перед параллельной разработкой все трое согласуют минимальный общий контракт.** Его подготовку организует участник 2, участник 3 отвечает за часть ИИ, участник 1 проверяет, что ответы позволяют построить интерфейс.

Результат участника 3: фронтенд получает полезные вопросы и структурированный предложенный черновик, диалог восстанавливается после обновления страницы, ошибка модели не уничтожает введённые сведения. ИИ-модуль не публикует карточки и не принимает предложения.

**Для независимой разработки используем следующий стартовый контракт данных.** Все три участника подтверждают его до реализации; последующие изменения согласуют вместе.

| Объект | Поля |
|---|---|
| `NeedCardDraft` | `title`, `problem`, `expectedResult`, `acceptanceCriteria[]`, `constraints`, `budgetAmount`, `currency`, `deadline` |
| `Need` | `id`, `ownerId`, `originalDescription`, поля `NeedCardDraft`, `status`, `createdAt`, `selectedProposalId` |
| `Proposal` | `id`, `needId`, `authorId`, `solutionDescription`, `implementationPlan`, `expectedResult`, `priceAmount`, `currency`, `priceNote`, `durationDays`, `scheduleNote`, `status`, `createdAt` |
| Ответ уточнения | `sessionId`, `questions[]`, `suggestedCard: NeedCardDraft`, `missingFields[]` |
| Ошибка API | `code`, `message`, `fieldErrors` |

В черновике поля могут быть пустыми. Для публикации обязательны название, описание проблемы, ожидаемый результат и хотя бы один критерий успешного решения. Бюджет и срок могут быть `null` и отображаться как «Обсуждается». Если сумма задана, валюта обязательна; денежные значения на сервере представлены `BigDecimal`. Полнота означает выполнение явных правил заполнения, а не процент уверенности модели.

В предложении обязательны описание решения, план реализации, ожидаемый результат, а также либо числовая цена, либо пояснение условий цены, и либо длительность, либо пояснение условий срока. Статусы предложения: `PENDING`, `ACCEPTED`, `REJECTED`. Идентификаторы, владельцев, даты создания и статусы назначает сервер; DTO записи не позволяет клиенту произвольно их менять. Публичные ответы карточки содержат утверждённые поля, а исходный текст и диалог доступны только владельцу.

| API | Ответственный | Назначение |
|---|---|---|
| `POST /api/auth/register` | 2 | Регистрация |
| `POST /api/auth/login` | 2 | Вход |
| `POST /api/auth/logout` | 2 | Выход |
| `GET /api/auth/me` | 2 | Текущий пользователь |
| `GET /api/auth/csrf` | 2 | Получение CSRF-токена для запросов браузера |
| `POST /api/needs` | 2 | Создание своего черновика из заполненной формы |
| `PUT /api/needs/{id}` | 2 | Обновление своего черновика |
| `POST /api/needs/{id}/publish` | 2 | Проверка и публикация |
| `GET /api/needs` | 2 | Каталог опубликованных карточек |
| `GET /api/needs/{id}` | 2 | Карточка; для черновика — доступ только владельцу |
| `GET /api/me/needs` | 2 | Собственные карточки, включая черновики |
| `POST /api/needs/{id}/proposals` | 2 | Предложение решения |
| `GET /api/needs/{id}/proposals` | 2 | Предложения для владельца карточки |

| `POST /api/clarifications/{id}/messages` | 3 | Следующий ответ пользователя в поле `text` |
| `GET /api/clarifications/{id}` | 3 | Восстановление своего диалога и предложенного черновика |

Сценарий передачи данных: ИИ сохраняет предложенный черновик в своей сессии → фронтенд переносит поля в редактор → пользователь проверяет и изменяет содержание → основной API сохраняет `Need` в статусе `DRAFT` → пользователь отдельно публикует карточку. Ручное заполнение использует тот же API карточек. Общие правила валидации полей используются основным и ИИ-модулями, но публикацию всегда проверяет основной бэкенд.

**Объединяем результат по этапам, не дожидаясь завершения всех задач.**

| Этап | Участник 1 | Участник 2 | Участник 3 | Проверяемый результат |
|---|---|---|---|---|
| 0 | Примеры экранов и JSON | Каркас, контракты, текущий пользователь | Контракт уточнения и заглушка | Приложение запускается, все знают формат данных |
| 1 | Формы, каталог, вход | Авторизация и карточки | API диалога с заглушкой и сохранением | Можно вручную создать и опубликовать карточку; диалог подключается отдельно |
| 2 | Экран уточнения и предпросмотр | Предложения и принятие | Настоящая модель, вопросы и валидация | Работает путь от краткого описания до опубликованной карточки |
| 3 | Подключение решений и ошибки | Проверки прав и конкурирующего выбора | Сбои модели и набор примеров | Полный пользовательский сценарий и демонстрация |

Участник 2 несёт наибольшую нагрузку. Если времени не хватает, сначала сокращаем дополнительные функции. Участник 3 самостоятельно доводит API, хранение и проверки доступа своего модуля, участник 1 — режим тестовых ответов и все состояния интерфейса. Передача одному человеку всей интеграции в конце не планируется.

**Работа с общими файлами требует коротких договорённостей.** Участник 1 владеет статическими файлами интерфейса, участник 2 — пакетами `identity`, `needs`, `proposals`, участник 3 — пакетом `clarification`. Общие DTO и настройки сборки меняются после согласования. Миграции разных модулей получают уникальные версии. Работа идёт в ветках по небольшим задачам; готовые части регулярно объединяются через pull request.

В MVP входят регистрация и вход, карточки, уточнение через ИИ, ручное редактирование, публикация, предложения и выбор одного решения. Избранное, аватары, XML-экспорт, платежи, рейтинги, уведомления и переписка между пользователями откладываются.

**MVP готов, когда команда воспроизводит следующий сценарий.**

1. Потребитель входит и пишет короткую потребность.
2. Получает вопросы ИИ, отвечает и видит более полную карточку.
3. Исправляет предложенные поля и явно публикует карточку.
4. Два других пользователя отправляют разные решения с условиями цены и сроков.
5. Потребитель видит оба предложения и принимает одно; второй выбор сервер отклоняет.
6. После обновления страницы сохраняются карточка, предложения и результат выбора.
7. Чужие черновики и диалоги недоступны; при отказе модели можно продолжить вручную.
